# Preserve Responses protocol semantics at the provider boundary

The Responses Provider will preserve the client's External Model ID and registered tool type in its output while separately tracking the Kiro Model ID and Kiro tool representation. Unknown metadata may pass through validation, but unsupported fields that alter conversation state, execution ownership, or the output contract will fail explicitly rather than being ignored. Before an SSE response begins, failures remain HTTP errors; after `response.created`, failures become a terminal `response.failed` event, and the provider will not retry the Kiro generation after any Responses event has been emitted. Usage is reported from the best available estimate instead of fabricated zero values, and reasoning effort is documented as a best-effort Thinking Budget rather than OpenAI-native reasoning.

The first implementation will reject unsupported Hosted Tools, remote media references, stateful response fields, service-tier promises, and structured-output formats instead of emulating them with prompts. Safe metadata fields may be accepted through an explicit allowlist. Client Tools retain their registered Responses type even when their Kiro representation uses a JSON-schema tool internally.

Every HTTP request receives a new response identity; the provider does not promise cross-request idempotency or stream resumption. Client disconnect cancels the upstream request. Account failover and generation retry are allowed only before the first Responses event is emitted, after which the current response terminates on failure.
